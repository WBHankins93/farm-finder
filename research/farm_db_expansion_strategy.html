Farm Database — National Expansion Strategy

Decision framework for scaling from 315 farms in LA/MS to nationwide coverage

Three Approaches, One Recommendation

The core tension: depth is what differentiates this database from every existing national directory. Expanding too fast sacrifices that. Expanding too slowly misses the window while competitors (Localize, Farmish) improve their coverage. The question is how to scale without diluting quality.

Option A: State-by-State

~2 states per research session

✓ Completeness per state is high

✓ Easy to track progress

✓ Matches state-level directories (every state has its own ag dept)

✗ 50 states = very long timeline

✗ Some states have 5 farms, others have 500 — uneven sessions

✗ Doesn't prioritize by market opportunity

Option B: Concentric Rings by Region

~1 region per research cycle

✓ Builds outward from existing coverage

✓ Natural shipping/travel zones for users

✓ Each ring is a launchable market

✓ Prioritizes adjacent states with similar farm culture

✗ Requires defining regions (not always clean boundaries)

✗ Some high-value markets (Pacific NW, Northeast) are far out

Option C: All at Once (National Sweep)

Broad but shallow

✓ "National" label from day one

✓ Can claim coverage everywhere

✗ This is exactly what Localize and LocalHarvest did — and it's their weakness

✗ Sacrifices the depth that differentiates your platform

✗ Impossible to verify quality across 50 states simultaneously

✗ Stale data problem from day one

Recommendation: Concentric Rings, Batched by State Pairs

The hybrid approach. Expand in geographic rings outward from your LA/MS base, but within each ring, batch by state pairs (or singles for large states). Each ring is a launchable market — meaning the platform could go live for "Gulf South" before you've touched the Pacific Northwest. This matches how users actually search: within their region and adjacent areas.

Why this wins Each ring produces a usable, launchable regional database. You don't need national coverage to launch — you need deep, trusted coverage in one region. Ring 0 (LA/MS) is already done. Ring 1 adds the Gulf South states that share the same farm culture, same growing seasons, and are within weekend-trip distance for your initial user base. By the time you hit Ring 2, the platform has traction and the data collection process is a proven, repeatable skill.

Every state expansion should follow the same source hierarchy we established for LA/MS. This is the protocol that should become a Claude Skill:

The key insight from LA/MS that applies everywhere Every state has a land-grant university with a cooperative extension service that maintains a farm directory. This is always the single highest-yield source. In Louisiana it was LSU AgCenter. In Alabama it's Auburn. In Georgia it's UGA. In Texas it's Texas A&M AgriLife. Start there every time — it's the equivalent of getting the government census before doing door-to-door canvassing.

Data Architecture Recommendation for Scale

The current spreadsheet-with-tabs model works for 315 farms. It won't work for 3,000. Before Ring 1 expansion, the data should move to a structure that supports the platform build.

Recommended Structure

ComponentCurrentRecommended at Scale
Storage formatExcel tabs by regionSingle normalized table (Supabase/Postgres) with region as a column
DeduplicationManual (some overlap between tabs)Unique key: farm name + state + parish/county
Geographic dataCity/Parish textGeocoded lat/lng for map rendering
Source trackingNotes column + audit tabSeparate source_references table (farm_id → source, date_verified)
Web presence scoreManual 1–10Semi-automated: check if website resolves, count social handles, flag online stores
Certification dataIn Notes columnSeparate certifications table (farm_id → cert_type, cert_body, verified_date)
Market presenceText fieldMany-to-many: farm_id → market_id linking table
Risk: Don't over-engineer the database before building the platform The spreadsheet is the right tool for research. The database is the right tool for the platform. The migration should happen when you're ready to build the app, not before. Premature database design without knowing the final schema is a time sink. Keep researching in spreadsheets, then do a single migration when the platform schema is locked.

This Should Become a Claude Skill

The research workflow we've now proven across LA/MS is a strong candidate for a reusable Claude Skill. Here's what it would codify:

Skill: farm-database-expansion

Trigger: "Expand the farm database to [state]" or "Research farms in [region]"

Inputs: Target state or region, existing database file path

Process: Execute the 10-step per-state protocol above, outputting a new spreadsheet tab + source audit entries

Outputs: Updated .xlsx with new tab(s), updated source audit tab, updated HTML report with new stats

Quality gate: No tab marked "complete" until all 10 steps are documented in the source audit

When to build the skill After completing Ring 1 (Alabama + East Texas + Arkansas + full Mississippi). By that point, you'll have run the protocol 4–5 more times and will know exactly which steps yield the most data, which sources are consistently high-quality, and where the process needs adjustment. Building the skill now would codify assumptions that haven't been tested outside LA/MS.
