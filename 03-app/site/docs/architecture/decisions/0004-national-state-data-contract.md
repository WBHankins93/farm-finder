# ADR-0004: National four-file state data contract

**Status:** Accepted
**Date:** 2026-07-15
**Deciders:** FarmFinder owner

## Context

The first state expansions committed seven files per state and mixed source
catalogs, coverage tables, manifests, and manual decisions into the review surface.
This increased pull-request size and encouraged state-specific logic. A missing-data
rule also risked removing legitimate small farms when only a name was available.
FarmFinder needs national scale without a stale, difficult-to-audit backlog.

## Decision

Use one national pipeline and exactly four committed files per state: `state.yaml`,
`entities.csv`, `decisions.csv`, and `report.md`. Raw evidence stays in managed,
versioned storage or staging tables. Derived QA views are regenerated by shared
code and are never committed as competing authorities.

Every named farm candidate is retained. Missing fields route the candidate to
`research_or_qa_queue`; only affirmative evidence of non-farm status, closure,
wrong jurisdiction, or duplicate identity may exclude it. Exclusions are retained
as decisions and immutable observations rather than deleted.

Collection can be batched by geographic region. Review, approval, and promotion
remain state-based. County-like geography uses the Census county-equivalent model
and FIPS identity rather than state-specific columns.

Once coverage review and county coverage pass, eligible rows may be handed to the
next pipeline stage with a derived eligible-record export. Unresolved rows remain
in the originating state's QA queue and in `entities.csv`; QA is deferred across
state collection, but it is still required to reach `record_verified` and approval.

## Options considered

### Keep seven files per state

Preserves the first implementation but increases reviewer burden and repository
clutter as fifty states are added.

### Collect all states and clean only after collection

Maximizes discovery throughput but allows parser mistakes, duplicates, and stale
evidence to compound across a large backlog.

### Four committed files with continuous normalization

Keeps raw discovery broad while applying shared normalization immediately, then
reviews and promotes one state at a time.

## Trade-off analysis

The four-file contract requires a migration and reliable managed evidence storage.
In exchange, it sharply reduces Git churn, gives reviewers one generated report,
and makes state behavior deterministic. Continuous normalization is slower than an
unreviewed nationwide dump but prevents systematic errors from multiplying.

## Consequences

- Adding a state changes at most four state files.
- State-specific collectors configure sources but cannot redefine retention or
  exclusion policy.
- Missing information increases QA backlog; it never lowers candidate coverage.
- QA backlog does not block the next state's collection or eligible-record handoff.
- Decisions and evidence must remain traceable after merges, corrections, and
  exclusions.
- Contract version 1 remains readable only during migration and is rejected for new
  state directories.

## Action items

1. Migrate Alabama and Texas to contract version 2.
2. Add retention-policy regression tests to CI.
3. Re-audit absence-based exclusions before state approval.
4. Promote states only through the shared approval fingerprint.
